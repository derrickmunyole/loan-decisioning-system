# 0005. Generic HTTP Idempotency-Key mechanism

## Status

Accepted

## Context

Milestone 1, Epic 1.4 needed `POST /applications` and `POST /applications/{id}/submit` to satisfy the roadmap's own done-criterion: "duplicate submit with the same Idempotency-Key returns the identical response without a double-create." This is the third of the roadmap's three distinct dedupe mechanisms — `consumed_event` (AMQP redelivery, Epic 1.3) and `inbox_message` (webhook redelivery, Milestone 5) solve different problems and must not be conflated with this one. The blueprint's data model literally lists `idempotency_key` as a column on `application`, but that only covers the create endpoint; submit (and, per the blueprint's API table, offer-accept in Milestone 5) needs the same semantics against an *existing* resource, which a single column on one row can't express.

## Decision

**Generic `idempotency_key` table in `platform-infrastructure`**, keyed on `(scope, idempotency_key)`, reused by any endpoint that needs "duplicate request produces exactly one effect, replay the original response." Rejected the blueprint's literal Application-row column: it doesn't generalize to submit or to offer-accept later, and would mean re-solving the same problem three times. `IdempotencyService.execute(scope, key, requestHash, responseType, operation)` is the one call a service makes, mirroring `OutboxEventPublisher.enqueue(...)`'s shape from ADR 0004.

**Row lock as the mutex, not caught-exception control flow.** The reserving call does `INSERT ... ON CONFLICT (scope, idempotency_key) DO NOTHING` inside the caller's transaction. `ON CONFLICT DO NOTHING` never throws, which matters: catching a `DataIntegrityViolationException` from a unique-constraint violation would mark the surrounding Spring-managed transaction rollback-only, making it unusable for the business logic that needs to run in the *same* transaction as the reservation. If the insert reserves 0 rows, a `SELECT ... FOR UPDATE` on the existing row blocks until the reserving transaction commits or rolls back (Postgres row-lock semantics under the default isolation level) — a concurrent duplicate genuinely waits for the first attempt to resolve, not just a best-effort race. If the row has vanished after that block (the first attempt rolled back), reservation is retried, bounded to 3 attempts before surfacing a 409 asking the caller to retry later.

**Business logic and the completion write share the reservation's transaction.** `IdempotencyService.execute` is itself `@Transactional`; the caller's `operation` supplier runs inside it, and the record is marked `COMPLETED` with the serialized response before the method returns. If the operation throws, the whole transaction — reservation included — rolls back, so a failed attempt doesn't permanently block reuse of the key. This is the same "shares the caller's transaction" principle ADR 0004 established for the outbox.

**Caller-assigned entity IDs, extended from the `Notification` lesson.** ADR 0004 documented the real bug where `Notification.id` was Hibernate-generated instead of the ID already handed to the caller. `Application` and `Document` follow the same caller-assigned-ID pattern here, but for a second, independent reason: `@Audited`'s SpEL only binds method *parameters*, not return values (see `AuditAspect`), so a service method wrapped by `IdempotencyService.execute(...)` — where the entity is created *inside* a lambda — has no way to reference a Hibernate-generated ID as the audit target. Generating the ID in the outer, non-audited method and passing it down as a parameter sidesteps this cleanly.

**Split command service to preserve `@Audited`'s AOP.** `ApplicationService.createDraft`/`submit` call `idempotencyService.execute(..., () -> applicationCommandService.create(...))`, where `ApplicationCommandService` is a *different* Spring bean than `ApplicationService`. This isn't cosmetic: if the `@Audited`-annotated business method lived on the same class that calls `idempotencyService.execute`, invoking it from the lambda would be a self-invocation that bypasses the AOP proxy entirely, and no audit row would ever be written. Same category of AOP-boundary trap as ADR 0004's listener/handler split, different cause (proxy self-invocation vs. transaction-commit timing).

**Document → application_version linkage.** The blueprint's data model ties `document` to `application_version`, but documents are uploaded during `DRAFT`, before a version exists. `Document.applicationVersionId` is nullable and stays null through `DRAFT`; at submit, every document belonging to the application is stamped with the newly created version's ID. Documents can only be uploaded while the application is `DRAFT` (same guard as `PATCH`), so this stamping always has a well-defined single point of occurrence in Epic 1.4's scope.

## Consequences

**A genuinely stuck reservation blocks its key indefinitely.** If a reservation is made and the surrounding request hangs (not crashes — a real crash drops the DB connection and Postgres rolls back the open transaction, releasing the lock) — e.g. business logic blocked on a downstream call with no timeout — a concurrent duplicate's `SELECT ... FOR UPDATE` blocks for as long as that hang lasts. Nothing in Epic 1.4 makes an external blocking call inside an idempotency-wrapped operation, so this isn't live yet, but it becomes a real risk once Milestone 3's credit-score client (or later, the mock payment provider) sits inside an idempotency-wrapped flow without a Resilience4j timeout. Revisit then, not now.

**Response replay is a full JSON round-trip, not a lightweight flag.** The cached response is deserialized back into the same DTO type on every replay. This is simple and correct for the response shapes in Epic 1.4, but assumes the response type is stable across a client's retry window — fine given `ApplicationResponse` doesn't change shape mid-request, but worth remembering if a future idempotent endpoint's response shape is expected to evolve.
