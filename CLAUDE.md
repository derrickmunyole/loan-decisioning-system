## Project state

**Milestone 1 is done (Epics 1.1–1.6).** 1.1: the Maven reactor exists with `platform-app` and `platform-common`, Docker Compose brings up Postgres/RabbitMQ/MinIO, and Flyway applies an empty baseline. 1.2: `platform-security` exists — 6-role enum, self-issued JWT auth (`POST /auth/login`), a `SecurityFilterChain` with endpoint-level role gates and method-level `@PreAuthorize` ownership checks, an `app_user` table, and a synthetic-user seeder (one demo user per role, see Commands below). 1.3: `platform-infrastructure` exists — transactional outbox (`OutboxEventPublisher.enqueue(OutboxPayload)`, typed payloads only, see ADR 0004), `OutboxRelay` publishing with confirms, RabbitMQ topology + DLX/retry, `consumed_event` dedupe, `@Audited` AOP-based audit logging, correlation-ID propagation, and a `SYSTEM_SERVICE`-principal aspect wrapping every `@RabbitListener`. 1.4: `applicant-origination` exists — `Applicant`/`Application`/`ApplicationVersion`/`Consent`/`Document` entities, the draft→submit flow (`POST /applications`, `PATCH /applications/{id}`, `POST /applications/{id}/submit`, `POST /applications/{id}/documents`, `GET /applications/{id}`, `GET /applications/{id}/timeline`), and a generic `idempotency_key` mechanism in `platform-infrastructure` (see ADR 0005) backing HTTP `Idempotency-Key` on create/submit — the third and last of the roadmap's three distinct dedupe mechanisms. Documents upload server-mediated to MinIO (server computes the checksum and pushes the bytes itself; no presigned URLs yet, see ADR 0006). `Application.status` was a direct DRAFT→SUBMITTED field set through Milestone 1, not routed through a workflow engine — that changed in Epic 2.1 (see below). `/internal/security-probe/**` has been removed now that real role-gated + ownership-checked endpoints exist; `/internal/plumbing-probe/**` remains until a real flow first publishes `notification.requested`. 1.5: `synthetic-data-generator/` exists — a `uv`-managed Python CLI (`synthetic-data-generator --count N`) that logs in as the seeded `applicant` user and drives the real REST API (create → patch draft → upload a document → submit) per application, dogfooding the same endpoints a real applicant would hit rather than inserting rows directly. `--scenario` shape flags from the roadmap's A.10 are deliberately deferred — nothing downstream consumes them until verification/decisioning exist in Milestones 2–3. 1.6: `docs/adr/` audited against the actual shipped code — ADR 0003 corrected (MinIO's native SDK, not AWS SDK v2), ADR 0006 added (server-mediated upload with server-computed checksum), ADR 0005 amended (per-caller scope construction, column widening). One real open gap was surfaced and deliberately not closed in 1.6: the module-boundary rule (`xxx.api`-only cross-module access) was enforced by convention only, no ArchUnit suite. **Closed as Milestone 2 prep, before Epic 2.1**: `ModuleBoundaryTest` in `platform-app` now enforces the rule for `infrastructure` and `origination` (extends naturally to future bounded-context modules; `common`/`security` are exempt as targets — shared kernel and framework-wired respectively, see ADR 0001's status update). Writing the rule surfaced a real pre-existing violation — `applicant-origination` reaching into `infrastructure.audit`/`infrastructure.idempotency` internals — fixed by relocating `Audited`, `IdempotencyService`, `RequestHash`, and the two idempotency exceptions into `infrastructure.api`.

**Milestone 2 — Workflow & Verification — is done (Epics 2.1–2.3).** 2.1: `workflow` module exists — `ApplicationStatus` relocated from `applicant-origination` into `workflow.api` and expanded from a 2-value placeholder to the full 16-state lifecycle in `docs/blueprint.md` §4, and `WorkflowTransitionService` validates every `from → to` edge against a fixed transition table, throwing `IllegalApplicationTransitionException` (mapped to 409) on an illegal one. The service is deliberately validation-only — no persistence, audit, or outbox side effects of its own; the caller keeps owning its entity mutation, `@Audited`, and outbox enqueue, all inside its own transaction, so atomicity is a property of shared transaction scope rather than something `WorkflowTransitionService` physically performs (see ADR 0007 for the alternatives this ruled out). `ModuleBoundaryTest` extends its `xxx.api`-only rule to cover `workflow`. 2.2: `workflow_task` + `GET /work-queue` (role-gated to `UNDERWRITER`/`OPERATIONS_ANALYST`, read-only — per-role scoping and resolve/retry actions are Epic 4.2's job) — a new `AmqpDedupeService` (`infrastructure.api`) generalizes the `consumed_event` pattern for listeners living outside `platform-infrastructure`, since `workflow`'s new DLQ listener (`NotificationRequestedDlqListener`) is the first one. Live verification during 2.2 found a real bug dating to Epic 1.3: `AcknowledgeMode.MANUAL` plus a channel-aware `@RabbitListener` signature meant nothing ever nacked a message on the failure path, so exhausted retries never actually reached the DLQ. Fixed by switching to `AcknowledgeMode.AUTO` (Spring Boot's default — `RabbitListenerConfig`'s override was deleted) and dropping the `Channel`/`deliveryTag` parameters from both listeners; see ADR 0004's amendment for the full story. `Application.status`/`ApplicationCommandService` and the notification success path are unaffected by that fix. 2.3: `verification` module exists — a single `application.submitted` consumer (`ApplicationSubmittedListener`/`Handler`; no intermediate `verification.requested`/`completed` events are published) runs deterministic identity + income checks (`SyntheticVerificationEngine`, `verification_case` rows) and drives `SUBMITTED→VERIFYING→UNDERWRITING` atomically in one transaction — this superseded the Epic 2.1 stopgap where `ApplicationCommandService.submit` drove the `SUBMITTED→VERIFYING` hop itself; `submit` now only owns `DRAFT→SUBMITTED`. Two new `origination.api` ports back this: `ApplicationVersionQueryService` (read, so verification can see declared submission fields) and `ApplicationTransitionService` (write, so verification can drive `Application` through the state machine) — neither module reaches into `origination`'s internal entities directly. Two sentinel values on `declaredEmployerName` act as this epic's synthetic input-shape signals (standing in for the roadmap's future generator `--scenario` flags): `SYNTHETIC_IDENTITY_MISMATCH` (business-outcome `FAILED` on the `IDENTITY` check — verification can't reroute status, only flag for underwriter review, so the application still reaches `UNDERWRITING`) and `SYNTHETIC_TRANSIENT_FAILURE` (a real retry via Spring AMQP's retry interceptor, backed by a `REQUIRES_NEW` `VerificationAttemptTracker` counter so the simulated failure's transaction rollback doesn't erase its own attempt count). `ModuleBoundaryTest` extends its rule to cover `verification`.

**Milestone 3 — Decisioning — is in progress (Epic 3.1 done).** 3.1: `decisioning` module exists — a new `UnderwritingSnapshot` (application-version-declared fields + verification evidence, serialized to a `facts_json` jsonb column) is created exactly once per application the moment it reaches `UNDERWRITING`. Triggered by a new `underwriting.requested` outbox event, published by `verification`'s existing `ApplicationSubmittedHandler` in the same transaction as the `UNDERWRITING` hop — this is a real intermediate event (unlike `verification.requested`/`verification.completed`, which 2.1/2.3 deliberately skipped), since `decisioning` is its first actual consumer. A new `verification.api` port, `VerificationEvidenceQueryService`, backs this the same way `origination.api`'s ports back `verification` (ADR 0007's "extract a port on the second real caller" pattern). Exactly-once is backed by a DB unique constraint on `application_version_id`, not just the handler's own existence check — the check is a fast path, the constraint is the real guarantee, proven by an integration test forcing a duplicate delivery with a fresh `eventId` (not a redelivery of the same message, so AMQP dedupe alone can't be what's stopping it). `decisioning`'s own DLQ reuses the existing generic `DeadLetterTaskHandler` in `workflow.workqueue`, which had to be parameterized by consumer name (previously hardcoded to notification's) so two DLQ listeners sharing it don't record dedupe rows under the wrong identity. `ModuleBoundaryTest` extends its rule to cover `decisioning`. ## Source of truth documents

Two documents in `docs/` define this project completely and must be read before making architectural decisions or starting a new milestone:

- `docs/blueprint.md` — the *what/why*. Product boundary, actors/permissions, functional requirements, the application state model, the full data model and entity relationships, API surface, async event catalog, architecture map, and non-functional requirements (correctness, idempotency, authorization, auditability, resilience, privacy, observability, testing).
- `docs/roadmap.md` — the *how/when*. Concrete technology choices for every part of the blueprint (Maven module layout, Spring Boot stack, outbox/RabbitMQ mechanics, state machine approach, security model, the two Python services) and the phased delivery plan (6 milestones broken into sprint-sized epics with explicit done-criteria), plus a risks/sequencing-traps section.
- `docs/adr/` — architecture decision records, one per major decision, written contemporaneously as the roadmap's Milestone 1.6 (and later epics) produce them.

Do not re-derive or re-decide anything already settled in these two files (e.g. hand-rolled state machine vs Spring Statemachine, module count, RabbitMQ topology, dedupe strategy) — treat them as locked unless the user explicitly reopens the decision. When a milestone's implementation surfaces a real gap or contradiction in these docs, update the docs rather than silently diverging from them in code.

## Architecture summary (see the roadmap for full detail)

- **Monorepo, polyglot.** One Java Maven multi-module reactor for the core app, sibling Python directories for two services, Docker Compose ties everything together.
- **Java/Spring Boot is the primary application** (Java 21, Maven, palantir-java-format — currently disabled in `.idea/palantir-java-format.xml`, expected to be enabled once the reactor exists). Modular monolith: one deployable (`platform-app`) hosting both REST controllers and RabbitMQ listeners, organized as ~7 Maven modules (`platform-app`, `platform-common`, `platform-infrastructure`, `platform-security`, `applicant-origination`, `workflow`, growing to include `verification`, `decisioning`, `offers`, `funding`, `notifications` as milestones require them). Modules must not import another bounded context's JPA entities/repositories directly — cross-module access goes through an `xxx.api` package, enforced by ArchUnit.
- **Two Python services, deliberately scoped**: a FastAPI `credit-score-service` (synchronous, deterministic weighted-formula scorer called by the Java decision engine — introduced at Milestone 3, not before) and a `synthetic-data-generator` CLI (offline, seeds demo data by calling the real REST API rather than faking terminal states — introduced at the end of Milestone 1).
- **Async backbone is RabbitMQ from the start**, implementing a transactional outbox: business writes and `outbox_event` rows share a DB transaction; a scheduled relay publishes with publisher confirms and marks rows published only inside the confirm callback; per-consumer DLX-backed queues feed dead-lettered messages into `workflow_task` ops items. Three separate dedupe mechanisms exist for three separate problems and must not be conflated: HTTP `Idempotency-Key` (client retries), `consumed_event` table (AMQP at-least-once delivery), `inbox_message` table (webhook redelivery).
- **State machine is hand-rolled** (enum + transition table + `WorkflowTransitionService`), not Spring Statemachine — see the roadmap's rationale before introducing that library.
- **Everything decision-related is immutable/append-only**: `ApplicationVersion`, `Decision`, `PolicyVersion`/`ScorecardVersion`/`PricingVersion`, `AuditEvent`, `UnderwritingSnapshot` are insert-only with no update path; a `Decision` always carries the exact snapshot/policy/scorecard/pricing/credit-score-model version IDs it was computed from.

## Delivery sequence

Work proceeds through the roadmap's 6 milestones in strict dependency order (Foundation → Workflow & Verification → Decisioning → Operations & Underwriter Actions → Lending Completion → Hardening). Within a milestone, its epics are the actual unit of work — each epic in the roadmap has an explicit done-criterion (a runnable/demoable/testable increment, not just code written); treat that criterion as the acceptance bar before considering an epic finished, even though this is an AI-assisted build where output is fast to produce.

One feature branch and one PR per epic; commit each logical piece of the epic separately within that branch rather than one lump commit, so the PR is reviewable commit-by-commit (see git history for the shape this takes in practice). **PRs in this repo are squash-merged, not merge-commit** — this predates and intentionally overrides Claude Code's global default (regular merge commit) established after Epic 1.4, kept for consistency with Epics 1.1–1.4's already-squashed history rather than introducing a visible seam partway through the project. The granular per-epic commits still exist forever on each PR's GitHub page for review purposes even after squashing; they just don't persist as separate objects in `master`'s own history.

## Commands

- Build the reactor: `./mvnw -DskipTests package` (drop `-DskipTests` once tests exist).
- Run a single test class: `./mvnw -pl platform-app test -Dtest=SomeClassNameTest`.
- Start local infra (Postgres, RabbitMQ, MinIO + bucket init): `cp .env.example .env` (first time only, then edit real values), `docker compose up -d`. RabbitMQ management UI is at `localhost:15672`; MinIO console at `localhost:9001`.
- Run the app against dockerized infra (IDE or CLI): `java -jar platform-app/target/platform-app.jar --spring.profiles.active=local`, with the same `.env` variables exported into the shell (`set -a; source .env; set +a`). Confirms up via `curl localhost:8080/actuator/health`.
- Log in as any of the 6 seeded synthetic users (`applicant`, `underwriter`, `operations_analyst`, `policy_admin`, `auditor`, `system_service`) via `POST /auth/login` with that username and the `SEED_USERS_PASSWORD` value from `.env`; the response's `token` is a bearer JWT.
- Seed demo applications against a running app: `cd synthetic-data-generator && uv sync` (first time only), then `SEED_USERS_PASSWORD=... uv run synthetic-data-generator --count N` (defaults: `--base-url http://localhost:8080`, `--username applicant`). Every application is created by the single seeded `applicant` user — `Applicant` is found-or-created by username, so N applications means N loop iterations against that one account, not N accounts.
- Lint/format the Python CLI: `cd synthetic-data-generator && uv run ruff check .` and `uv run ruff format .`. `ruff` is the shared convention for this repo's Python components (config lives in each component's own `pyproject.toml`); `credit-score-service` should adopt the same block when it's added in Milestone 3.

This reactor deliberately does **not** inherit from `spring-boot-starter-parent` (it needs its own multi-module dependency management instead), which silently loses two defaults that parent normally sets — both already bitten us once, so re-check before assuming either is on:
- The `spring-boot-maven-plugin`'s `repackage` goal is **not** auto-bound to `package` — `platform-app/pom.xml` binds it explicitly via `<executions>`. A future module needing its own executable jar needs the same binding, or `mvn package` silently produces a jar with no `Main-Class`.
- The `-parameters` javac flag is **not** on by default — set via `maven.compiler.parameters=true` in the root POM's `<properties>`. Without it, reflection-based parameter-name lookups fail silently rather than erroring, which broke `@PreAuthorize("#username == ...")` in `platform-security` (SpEL couldn't resolve the parameter name, so the check silently denied everyone). Also remember Maven's compiler plugin only recompiles *stale* sources — a `pom.xml` property change like this doesn't force recompilation on its own; run `./mvnw clean` first if a compiler-flag change doesn't seem to take effect.

Any future `@RabbitListener` must follow the pattern in `NotificationRequestedListener`/`NotificationRequestedHandler` (see ADR 0004): the listener method calls a separate `@Transactional` handler method and only acks *after* that call returns. Acking from inside the `@Transactional` method itself acks before Spring's transaction interceptor actually commits (the interceptor commits after the method returns to its caller, not as the method's last statement), which is the exact "ack before commit" trap the roadmap warns against.

`SecurityConfig` permits `/error`. Without it, any `@Valid` validation failure on an authenticated endpoint returns 403 instead of the real 400: `response.sendError()` forwards internally to `/error`, but `JwtAuthenticationFilter` (a `OncePerRequestFilter`) skips `ERROR` dispatches by default, so that internal forward reaches Spring Security's `.anyRequest().authenticated()` with no `Authentication` in context and gets denied. Found via live manual verification in Epic 1.4 (it reproduced on the Epic 1.3 probe endpoint too — this bug predates 1.4, it just hadn't been exercised).

If a shell-profile `DB_PASSWORD` is already exported before running `set -a; source .env; set +a`, `source` still overwrites it with `.env`'s value for that shell — but the running Postgres container was `POSTGRES_PASSWORD`-initialized from whatever `DB_PASSWORD` docker-compose resolved at *its own* creation time (shell env takes precedence over `.env` there too), which may not be the same value. If they've drifted, the app fails to start with a Postgres `password authentication failed` error that looks like a credentials/config problem but is really just `.env` and the shell profile disagreeing about which password is real. Found live-verifying Epic 1.5's generator — resolved by checking `env | grep DB_PASSWORD` against `.env`'s value and exporting the one Postgres was actually initialized with.

`ModuleBoundaryTest` can silently miss a real cross-module violation when the only thing crossing the boundary is a `public static final String` constant (e.g. a queue name). `javac` inlines compile-time String/primitive constants directly into the referencing class's bytecode/constant pool — no `getstatic` instruction survives, so ArchUnit's bytecode-level dependency analysis never sees an edge back to the declaring class, and `noClasses().should().dependOnClassesThat(...)` passes even though the source clearly imports across the boundary. This is why `RabbitQueueNames` exists in `infrastructure.api` specifically for listeners outside `platform-infrastructure` to reference queue names — `RabbitTopologyConfig` (internal, `infrastructure.messaging`) has the same constants, but referencing it directly from another module is exactly the class of violation the inlining hides. Found while building Epic 3.1's `decisioning` consumer: `verification`'s existing `ApplicationSubmittedListener` already referenced `RabbitTopologyConfig.APPLICATION_SUBMITTED_QUEUE` directly, an undetected pre-existing instance of this same gap. Left uncorrected there (out of scope for 3.1); new listeners should use `RabbitQueueNames`, not `RabbitTopologyConfig`, and this class of gap can't be caught by re-running ArchUnit — only by grepping for cross-module imports of `RabbitTopologyConfig` by hand.
